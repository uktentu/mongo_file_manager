Overview

What & Why

The MongoDB Document Seeder solves a specific, recurring problem in regulatory reporting: how do you safely version config files, SQL queries, and templates that multiple regulation repos share, without coupling those repos to each other?

🎯

The Problem

Regulation repos (MAS-TRM, BASEL, DORA) need to share config files and SQL queries with a central report generator. Without a versioned store, changes break old reports silently.

🏗️

The Solution

A central seeder service that stores every version of every bundle in MongoDB + GridFS, with checksums, audit logs, and automatic CREATE / MODIFY / SKIP routing.

⚡

For ReportGen

ReportGen reads files directly from MongoDB in memory — no download step, no temp files, ~5ms per file. The SDK client handles everything transparently.

🔒

Guarantees

Every file has a SHA-256 checksum verified on read. Modifications are atomic on replica sets. Orphaned GridFS files are automatically cleaned up on failure.

Why a separate service instead of putting files in Git? Git is for code history, not binary/config distribution. A versioned store lets ReportGen fetch the exact config version it needs without cloning repos, and provides a machine-readable audit log that satisfies regulatory traceability requirements. Checksums guarantee the file bytes haven't been corrupted in transit or at rest.

Architecture

System Architecture

External regulation repos never write to MongoDB directly. They push file content to this service via HTTP API or CLI. The seeder owns storage, versioning, and integrity.

Why this layered architecture?

  • CLI + API are thin shells — all business logic lives in services, making it testable independently of the transport layer.
  • Services are stateless — they call get_db() per request; the connection pool is managed by DatabaseManager.
  • Utils are pure functions — checksum, retry, validator have no side effects, making them composable and easy to test in isolation.
  • SDK sits beside the services — ReportGen can import it directly when co-located, skipping HTTP entirely.

Technology

Technology Decisions

Every technology choice has a specific reason. Here's what we used and why it beats the alternatives.

🍃 MongoDB + GridFS
Storage backbone for metadata + binary files
  • GridFS handles files of any size without a 16MB BSON limit
  • Flexible schema lets each regulation add custom fields to configs
  • Replica set transactions give atomicity for version deactivation + insert
  • Native ObjectId references between metadata and GridFS chunks
  • Atlas support means managed infra for prod with no schema migrations
⚡ FastAPI
REST API layer
  • Pydantic models give automatic request body validation and docs
  • Async-first with Uvicorn/Gunicorn for high concurrency
  • StreamingResponse for ZIP and file exports without buffering
  • Lifespan context for clean startup/shutdown of DB connection
  • Auto-generated Swagger UI at /api/docs
🖱️ Click + Rich
CLI layer
  • Click handles argument parsing, type coercion, and help text cleanly
  • Rich provides beautiful tables and panels for output
  • Same service layer used by both CLI and API — no duplication
  • Works well in CI/CD pipelines with machine-parsable exit codes
📐 Pydantic v2
Data models and validation
  • Schema validation at API boundaries (request bodies)
  • MetadataDocument.to_mongo_dict() serializes directly to BSON-ready dict
  • Field defaults enforce invariants (version ≥ 1, timestamps auto-set)
  • Type annotations serve as living documentation
🔄 Append-Only Versioning
Version model
  • Old versions are deactivated, not deleted — full audit trail preserved
  • Any historical version can be fetched or exported at any time
  • Partial unique index enforces exactly one active version per composite key
  • Cleanup is a separate, controlled operation with dry-run support
🔑 Composite report_id
Record identifier
  • Deterministic: csi_id_region_regulation_stem is always the same for the same inputs
  • Human-readable in logs, making debugging much easier than opaque UUIDs
  • Stable across re-seeds — the same bundle always gets the same ID
  • 4-part composite key prevents cross-contamination between different configs
Core Flow

Seeding Flow

The 5-step seeding pipeline pre-validates every bundle before touching the database. A single bad bundle never blocks the rest.

1

Load & Parse YAML Manifest

Read seed.yaml with yaml.safe_load(). The base_dir is set to the manifest's parent directory — all file paths in the manifest are resolved relative to it, enabling portability.

2

Validate Manifest Structure

Confirm root is a dict with a non-empty bundles list. Fail fast here before wasting time on individual bundle checks.

3

Pre-validate ALL Bundles — No DB Writes Yet

Run all 6 validation layers on every bundle before any database operation. Bundles that fail validation are marked as errors; valid bundles proceed. This means bundle #5's error never stops bundles #1–4 from seeding. The parsed JSON config object is also carried forward here to avoid re-reading the file.

4

Route Each Bundle: CREATE / MODIFY / SKIP

For each validated bundle: compute SHA-256 checksums, look up the active record by composite key, then route. See the Composite Key Routing section for the full decision tree.

5

Return Structured Result

Returns {"created": N, "updated": N, "skipped": N, "failed": N, "total": N, "details": [...], "errors": [...]}. Per-bundle details include report_id, version, and reason — enough to confirm exactly what changed.

Why pre-validate all bundles before any DB write? If validation were interleaved with DB writes, a failure on bundle #3 could leave bundles #1 and #2 committed while #3+ are not — a partial, hard-to-debug state. Pre-validation collects all errors upfront, then the DB phase only processes bundles we know are valid. This separates concerns cleanly and makes re-runs safe.

Routing

Composite Key Routing

The 4-part composite key is the heart of the system. It uniquely identifies every logical document bundle without requiring callers to manage IDs.

Composite Key = csi_id + region + regulation + json_config filename
All four parts are required. The 4th part (json_config filename) allows the same regulation to have multiple distinct report configs.
flowchart LR IN["Bundle Input\ncsi_id, region, regulation\njson_config filename+content\nsql_file, template"] KEY["Build Composite Key\ncsi_id + region + regulation\n+ json_config filename"] LOOKUP["Query metadata collection\nfind active record matching key"] NONE["No record found"] FOUND["Record found"] CHK1["SHA-256: json_config\nstored vs computed"] CHK2["SHA-256: sql_file\nstored vs computed"] CHK3["SHA-256: template\nstored vs computed"] ANY{"Any checksum\nchanged?"} CREATE(["CREATE\nNew composite report_id\nAll files uploaded\nversion = 1"]) SKIP(["SKIP\nNothing written\nIdempotent re-run"]) MODIFY(["MODIFY\nOnly changed files re-uploaded\nNew version appended\nOld version deactivated"]) IN --> KEY --> LOOKUP LOOKUP --> NONE --> CREATE LOOKUP --> FOUND --> CHK1 & CHK2 & CHK3 --> ANY ANY -- No --> SKIP ANY -- Yes --> MODIFY

report_id Format

Format:   {csi_id}_{region}_{regulation}_{json_config_stem}
Example:  CSI-001_APAC_MAS-TRM_mas_trm_report

Breakdown:
  CSI-001      ← csi_id  (the project/system identifier)
  APAC         ← region  (geographic scope)
  MAS-TRM      ← regulation (the regulatory framework)
  mas_trm_report ← filename stem of the json_config (without .json)

Why include the json_config filename in the composite key? The same (csi_id, region, regulation) triple can legitimately have multiple distinct report configs — e.g. a summary report and a detailed report for the same regulation. The 4th key part (json_config filename) separates these without requiring callers to manage explicit IDs. This is why history and cleanup queries must use all 4 parts — using only 3 would mix logically separate records.

Delta Upload on MODIFY

Only changed files are re-uploaded to GridFS. Unchanged files keep their existing GridFS ObjectIds, saving storage and bandwidth.

Validation

6-Layer Validation Pipeline

All validation runs before any database write. Each layer catches a different class of error, and all errors are collected before reporting.

Why path traversal protection in validation? Without it, a malicious seed.yaml could reference ../../etc/passwd and upload system files to GridFS. The base_dir check ensures all file paths resolve inside the manifest's directory, regardless of ../ sequences in the path.

Safety

GridFS & Safety Mechanisms

Files are uploaded to GridFS with retry, orphan tracking, and checksum storage. If a metadata insert fails after files are uploaded, the orphan tracker cleans up the GridFS files.

sequenceDiagram participant SS as seed_service participant OT as GridFSOrphanTracker participant GS as gridfs_service participant RET as retry decorator participant GFS as MongoDB GridFS participant META as metadata collection SS->>OT: create tracker SS->>GS: upload_to_gridfs(json_config) GS->>RET: attempt 1 RET->>GFS: bucket.put(file bytes) GFS-->>RET: gridfs_id GS->>OT: tracker.track(gridfs_id) GS-->>SS: gridfs_id ✓ SS->>GS: upload_to_gridfs(sql_file) GS->>RET: attempt 1 — network blip RET->>RET: sleep 0.5s RET->>GFS: attempt 2 GFS-->>RET: gridfs_id GS->>OT: tracker.track(gridfs_id) GS-->>SS: gridfs_id ✓ SS->>META: insert_one(metadata doc) alt Insert succeeds META-->>SS: ok SS->>OT: tracker.clear() — no orphans else Insert fails META-->>SS: error SS->>OT: tracker.cleanup() OT->>GFS: delete(json_config_id) OT->>GFS: delete(sql_file_id) SS-->>SS: raise DatabaseError end

Retry Strategy

AttemptDelay before retryTriggered by
1st— (immediate)Any retryable exception
2nd0.5sAutoReconnect, ConnectionFailure, NetworkTimeout, ServerSelectionTimeoutError
3rd1.0sSame
Exhausted—Raises DatabaseError

Why the orphan tracker pattern instead of transactions for GridFS? MongoDB transactions do not cover GridFS — GridFS operates on two separate collections (fs.files and fs.chunks) using its own internal locking. So even with replica set transactions, GridFS uploads are outside the transaction boundary. The orphan tracker compensates: it tracks every uploaded GridFS ID and bulk-deletes them if the subsequent metadata insert fails. On replica sets the metadata operations are transactional; GridFS cleanup is best-effort on failure.

Versioning

Version History & Cleanup

Every change produces a new version document. Old versions are deactivated (not deleted), enabling full point-in-time reconstruction. Cleanup is a controlled, separate operation.

flowchart TD subgraph VersionModel["Append-Only Version Model"] V1["version=1\nactive=false\nreport_id: CSI-001_APAC_MAS-TRM_…\naudit: CREATED, DEACTIVATED"] V2["version=2\nactive=false\nreport_id: CSI-001_APAC_MAS-TRM_…\naudit: MODIFIED, DEACTIVATED"] V3["version=3\nactive=true\nreport_id: CSI-001_APAC_MAS-TRM_…\naudit: MODIFIED"] V1 -->|"Superseded by v2"| V2 -->|"Superseded by v3"| V3 end subgraph CleanupModes["Cleanup Modes"] CM1["purge_old_versions\nkeep N most recent per record\nreport_id scoped"] CM2["purge_all_old_versions\nglobal sweep — all composite keys\nuses 4-part grouping"] CM3["purge_by_age\npurge inactive records\nolder than N days"] end subgraph PurgeSteps["Purge Steps per version"] P1["Delete json_config from GridFS"] P2["Delete sql_file from GridFS"] P3["Delete template from GridFS"] P4["delete_one metadata doc"] P1 & P2 & P3 --> P4 end subgraph Guards["Safety Guards"] G1["active=true versions NEVER purged"] G2["dry_run=True — preview only, no writes"] G3["keep_versions respected — at least N inactive kept"] end CM1 & CM2 & CM3 --> PurgeSteps PurgeSteps --> Guards

Why append-only instead of update-in-place? Regulatory systems require auditability — you need to prove what config was active at any point in time. Update-in-place destroys that history. With append-only versioning, an auditor can query any historical version and verify the exact file bytes that were used to generate a report, backed by SHA-256 checksums. Cleanup is a separate, explicit operation that regulators can disable entirely if needed.

report_id (partial: active=true)Unique partialEnforces exactly one active version per report_id at DB level

Why partial unique indexes? A regular unique index on report_id would prevent multiple versions of the same record — which we need for the version history. A partial unique index on {active: true} only enforces uniqueness among active documents, allowing unlimited inactive versions of the same report_id. This is the right tool for append-only versioning.

Integration

ReportGen Integration

ReportGen has two ways to access files. The direct MongoDB path is recommended when co-located — it reads from GridFS in memory with zero HTTP overhead and no temp files.

Direct MongoDB (Recommended)

ReportGen connects to the same MongoDB instance and reads files directly from GridFS using ReportGenClient. Files arrive as bytes in memory — no disk I/O, no temp files, ~5ms per file.

ReportGen calls GET /api/records/{id}/files/{key} to stream a file over HTTP. Works across networks and VPCs. ~50–200ms per file depending on network latency.

Direct MongoDB — Code Flow

# ReportGen imports the SDK client (co-located scenario)
from src.sdk.client import ReportGenClient

with ReportGenClient.from_env() as client:
    # All reads happen in memory — no temp files
    config = client.get_json_config("CSI-001_APAC_MAS-TRM_mas_trm_report")
    sql    = client.get_sql_query("CSI-001_APAC_MAS-TRM_mas_trm_report")
    tmpl   = client.get_template("CSI-001_APAC_MAS-TRM_mas_trm_report")

    # config is already a Python dict — no json.loads() needed
    # sql is already a Python string — no file.read() needed
    report_name = config["report"]["name"]

    # Execute against your data database
    data = execute_query(sql, params={"start": "2026-01-01"})
    output = render(tmpl, data=data, config=config)

Why include the repo as a dependency instead of downloading files? The old pattern — download config file, store in /tmp, read, then clean up — has multiple failure modes: disk full, permission errors, stale temp files if the process crashes, and race conditions under concurrent access. Direct MongoDB reads eliminate all of these: the file bytes come straight from GridFS into Python memory, processed, and discarded. No temp files = no cleanup, no disk I/O, no race conditions.

GridFS storage: File bytes are stored in fs.chunks in 255 KB pieces. fs.files holds metadata (filename, contentType, checksum, upload_date). The metadata collection holds ObjectId references to fs.files entries.
